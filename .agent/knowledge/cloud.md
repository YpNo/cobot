# Part 1 — Google Cloud

## Google Cloud IAM and least privilege
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/roles-overview] IAM has three role types: basic roles (broad access), predefined roles (granular, per service, managed by Google) and custom roles (a user-specified permission list).
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/roles-overview] The legacy basic roles are Owner (`roles/owner`), Editor (`roles/editor`) and Viewer (`roles/viewer`); newer basic roles Admin, Writer and Reader exist beside them.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/roles-overview] "In production environments, do not grant basic roles unless there is no alternative": basic roles include thousands of permissions across all services.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/roles-overview] Custom roles are created at organization or project level only (not folders); quota 300 per organization and 300 per project.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/conditions-overview] IAM Conditions are CEL expressions on resource type, resource name, resource tags (`resource.matchTag`) and date/time; deny-rule conditions recognise resource tag functions only.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/conditions-overview] Conditions cannot be used when granting Owner, Editor or Viewer, nor on `allUsers` or `allAuthenticatedUsers`; keep under 100 conditional bindings per allow policy; a conditional binding does not override an unconditional one; Cloud Storage buckets need uniform bucket-level access.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/deny-overview] Deny policies are guardrails attached to an organization, folder or project and inherited; IAM always checks deny policies before allow policies; up to 500 deny policies and 500 rules per resource; permissions use `SERVICE_FQDN/RESOURCE.ACTION` (for example `iam.googleapis.com/roles.delete`) and only some permissions can be denied.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/pam-overview] Privileged Access Manager grants just-in-time temporary role elevation through entitlements (requesters, justification, roles, maximum duration) on projects, folders and organizations; the legacy basic roles are not supported; grants stay in Cloud Audit Logs.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/best-practices-service-accounts] "We recommend that you avoid using service account keys whenever possible": a key is a non-repudiation threat and anyone who holds it can use it; alternatives are an attached service account, Workload Identity Federation (for GKE and for other clouds or CI) and impersonation with user credentials, which logs the acting principal.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/best-practices-service-accounts] Create a dedicated service account per application and avoid the default service accounts (they cannot be recreated once deleted); the org policy `constraints/iam.automaticIamGrantsForDefaultServiceAccounts` disables their automatic Editor grant; key creation and key upload have their own disable constraints.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/service-agents] A service agent is a Google-managed account a service uses to act on your resources; the typical email is `service-PROJECT_NUMBER@gcp-sa-SERVICE.iam.gserviceaccount.com`, the Google APIs Service Agent is `PROJECT_NUMBER@cloudservices.gserviceaccount.com`; the primary role is granted automatically at creation; "both the creation time and the email address format for service agents are subject to change".
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/create-service-agents] Service agents can be created before first use with `gcloud beta services identity create --service=SERVICE.googleapis.com --project=P` or `gcloud workload-identity service-agents generate`; the listed role is not granted automatically by that path.

## Workload Identity Federation
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/workload-identity-federation] Workload Identity Federation gives external workloads access without service account keys through the Security Token Service (OAuth 2.0 token exchange); one pool per non-Google environment is recommended; providers exist for AWS, Entra ID, GitHub, GitLab, Kubernetes, Okta, AD FS, Terraform, X.509 and any OIDC or SAML 2.0 IdP.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/workload-identity-federation] Attribute mappings are `TARGET=SOURCE_EXPRESSION` in CEL; `google.subject` is required and at most 127 characters; up to 50 custom `attribute.NAME`; an attribute condition is a CEL expression that must evaluate to true for the credential to be accepted and is what restricts which identities may authenticate.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/workload-identity-federation] Two access methods: direct resource access (recommended; some APIs have limitations) and service account impersonation (the account needs `roles/iam.workloadIdentityUser`); principals are `principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/POOL/subject/SUBJECT` and `principalSet://…/attribute.NAME/VALUE`, always with the project number.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines] GitHub Actions issuer `https://token.actions.githubusercontent.com/`, GitLab SaaS issuer `https://gitlab.com`; map at least `google.subject=assertion.sub`; GitHub claims include `repository`, `repository_id`, `repository_owner`, `repository_owner_id`, and the page advises the numeric `*_id` fields because names can be reused; GitLab claims include `sub`, `namespace_id`, `project_id`, `user_id`, `environment`, `ref_path`.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines] An attribute condition restricting the GitHub organization is required (`assertion.repository_owner=='ORG'`, optionally `&& assertion.ref=='refs/heads/main'`); GitLab example `assertion.namespace_id=='GROUP_ID' && assertion.environment=='production'`; the `gcp-` prefix is reserved in pool and provider IDs.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines] `gcloud iam workload-identity-pools create POOL --location=global` then `gcloud iam workload-identity-pools providers create-oidc PROVIDER --location=global --workload-identity-pool=POOL --issuer-uri=… --attribute-mapping=… --attribute-condition=…`.
- [verified 2026-11-08 · src: https://github.com/google-github-actions/auth] `google-github-actions/auth@v3`: Direct Workload Identity Federation is preferred (no proxy service account); `workload_identity_provider` is `projects/NUMBER/locations/global/workloadIdentityPools/POOL/providers/PROVIDER`; `service_account` is omitted for direct WIF; the job needs `id-token: write` and `contents: read`; "Always add an Attribute Condition to restrict entry into the Workload Identity Pool".

- [verified 2026-11-08 · src: https://raw.githubusercontent.com/hashicorp/terraform-provider-google/main/website/docs/r/google_project_iam.html.markdown] Members are `user:`, `serviceAccount:`, `group:`, `domain:`; a `condition` block has `title`, `description`, `expression` (CEL); an out-of-band change to the condition makes Terraform see a different resource.

- [verified 2026-11-08 · src: https://raw.githubusercontent.com/GoogleCloudPlatform/cloud-foundation-fabric/master/modules/project/service-agents.yaml] Fabric's agent catalogue template is `service-${project_number}@gcp-sa-<name>.${universe_domain}iam.gserviceaccount.com`; only `cloudservices` and the legacy `cloudbuild-sa` lack the placeholder.

- [verified 2026-11-08 · src: https://raw.githubusercontent.com/googleapis/google-cloud-go/main/auth/internal/internal.go] Go auth: `UniverseDomainEnvVar = "GOOGLE_CLOUD_UNIVERSE_DOMAIN"`, `DefaultUniverseDomain = "googleapis.com"`; on GCE the metadata server supplies it.

- [verified 2026-11-08 · src: https://sources.debian.org/src/python-google-api-core/2.23.0-1/google/api_core/universe.py] Python api-core: precedence client option, then `GOOGLE_CLOUD_UNIVERSE_DOMAIN`, then `googleapis.com`; `compare_domains` raises `UniverseMismatchError` when the configured universe differs from the credentials' universe.

## GKE
- [verified 2026-11-08 · src: https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-overview] Autopilot manages nodes, scaling and security; Regular channel by default, vertical Pod autoscaling and Dataplane V2 on, nodes scale to zero; general-purpose Pods are billed per Pod resource request, hardware-specific Pods per node plus a premium.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/kubernetes-engine/docs/concepts/autopilot-security] Autopilot blocks privileged containers, host namespaces, `hostNetwork`, SSH to nodes and `spec.externalIPs`; hostPath only read-only `/var/log`; drops `CAP_NET_RAW`; `NET_ADMIN` needs `--workload-policies=allow-net-admin`.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/kubernetes-engine/docs/concepts/release-channels] Channels Rapid, Regular (default), Stable, Extended; Regular about two months after Rapid, Stable three to four months after Regular; Extended gives up to 24 months per minor; Rapid is outside the SLA; "No channel" is removed on 2027-06-14.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/kubernetes-engine/docs/release-notes] Defaults for new clusters (notes to 2026-11-03): Rapid 1.37.1-gke.1697000, Regular 1.36.4-gke.2046003, Stable 1.35.8-gke.1439001, Extended 1.36.4-gke.2046003; minors 1.34 to 1.37 on Rapid and Regular, 1.34 to 1.36 on Stable, 1.32 to 1.37 on Extended.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity] The pool is `PROJECT_ID.svc.id.goog`; a Kubernetes service account is `principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/PROJECT_ID.svc.id.goog/subject/ns/NAMESPACE/sa/KSA` and a namespace `principalSet://…/namespace/NAMESPACE`; the GKE metadata server DaemonSet intercepts `metadata.google.internal`; `hostNetwork` pods do not get it.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/kubernetes-engine/docs/how-to/workload-identity] Direct IAM principal identifiers are the recommended method; cluster flag `--workload-pool=PROJECT_ID.svc.id.goog`, node pool `--workload-metadata=GKE_METADATA`; the linking alternative needs `roles/iam.workloadIdentityUser` on the IAM service account for `serviceAccount:PROJECT_ID.svc.id.goog[NS/KSA]` plus the `iam.gke.io/gcp-service-account` annotation.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api] GatewayClasses `gke-l7-global-external-managed`, `gke-l7-regional-external-managed`, `gke-l7-rilb` (internal), `gke-l7-gxlb` (classic), multi-cluster `-mc` variants; the single-cluster controller is Google-hosted and enabled by default.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploying-gateways] Gateway API needs a VPC-native cluster and the `HttpLoadBalancing` add-on; Standard enables it with `--gateway-api=standard`; "GKE Gateway is always enabled on Autopilot clusters"; manifests use `gateway.networking.k8s.io/v1`.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/kubernetes-engine/docs/how-to/private-clusters] `--enable-private-nodes` (needs `--enable-ip-alias`), `--enable-private-endpoint`, `--enable-master-authorized-networks --master-authorized-networks CIDRs`, `--enable-dns-access`; private nodes reach the internet through Cloud NAT; Private Google Access is on unless Shared VPC; the DNS-based control-plane endpoint is recommended.
- [verified 2026-11-08 · src: https://docs.cloud.google.com/kubernetes-engine/docs/how-to/hardening-your-cluster] Shielded nodes and secure boot are always on in Autopilot; Container-Optimized OS is the default (Standard) and only (Autopilot) node image; legacy ABAC is disabled by default; PodSecurity admission enforces the standards; Workload Identity Federation for GKE is the recommended API authentication; Binary Authorization validates images, GKE Sandbox uses gVisor.

## Pod Security Standards
- [verified 2026-11-08 · src: https://kubernetes.io/docs/concepts/security/pod-security-standards/] Three cumulative profiles: Privileged, Baseline (no hostNetwork/hostPID/hostIPC, no privileged, no hostPath, seccomp not Unconfined, a short capability add list) and Restricted (Baseline plus: volumes limited to configMap, csi, downwardAPI, emptyDir, ephemeral, persistentVolumeClaim, projected, secret; `allowPrivilegeEscalation: false`; `runAsNonRoot: true` and no `runAsUser: 0`; `seccompProfile.type` explicitly `RuntimeDefault` or `Localhost`; capabilities drop ALL, add at most NET_BIND_SERVICE).
- [verified 2026-11-08 · src: https://kubernetes.io/docs/concepts/security/pod-security-admission/] Pod Security Admission is stable since v1.25; namespace labels `pod-security.kubernetes.io/<enforce|audit|warn>: <privileged|baseline|restricted>` with optional `…-version: <minor|latest>`; enforce rejects, audit annotates, warn warns; exemptions by username, RuntimeClass or namespace.
- [verified 2026-11-08 · src: https://kubernetes.io/docs/tasks/configure-pod-container/security-context/] `readOnlyRootFilesystem` mounts the root filesystem read-only; `allowPrivilegeEscalation` defaults to true when unset and cannot be false with `privileged` or CAP_SYS_ADMIN; container-level securityContext overrides pod-level; an omitted `runAsGroup` means primary group root (0); capabilities are named without the `CAP_` prefix.

## Resources, probes, scheduling
- [verified 2026-11-08 · src: https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/] Requests drive scheduling and are reserved by the kubelet; CPU limits are enforced by throttling, memory limits by OOM kills; a limit without a request copies the limit as the request; `0.1` CPU equals `100m`; the page gives no recommendation to omit CPU limits.
- [verified 2026-11-08 · src: https://kubernetes.io/docs/concepts/workloads/pods/pod-qos/] QoS: Guaranteed (every container has CPU and memory limits equal to requests), Burstable (at least one request or limit), BestEffort (none); eviction order under pressure BestEffort, Burstable, Guaranteed; pod-level resources are beta since v1.34.
- [verified 2026-11-08 · src: https://kubernetes.io/docs/reference/kubernetes-api/workload-resources/pod-v1/] Probe defaults: `periodSeconds` 10, `timeoutSeconds` 1, `failureThreshold` 3, `successThreshold` 1 (must be 1 for liveness and startup).
- [verified 2026-11-08 · src: https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/] A failed liveness probe restarts the container; a failed readiness probe removes the pod from Service endpoints; HTTP 200–399 is success; a startup probe's `failureThreshold × periodSeconds` must cover the worst start; readiness runs for the whole lifetime; mechanisms exec, httpGet, tcpSocket, grpc (plaintext by default).
- [verified 2026-11-08 · src: https://kubernetes.io/docs/tasks/run-application/configure-pdb/] PodDisruptionBudget is `policy/v1` with exactly one of `minAvailable` or `maxUnavailable` (number or percentage); `unhealthyPodEvictionPolicy: AlwaysAllow` (stable since 1.31) lets unhealthy pods be evicted during a drain and is recommended; deleting a Deployment bypasses the budget.
- [verified 2026-11-08 · src: https://kubernetes.io/docs/concepts/scheduling-eviction/topology-spread-constraints/] `topologySpreadConstraints`: `maxSkew` (required), `topologyKey`, `whenUnsatisfiable` (`DoNotSchedule` default or `ScheduleAnyway`), `labelSelector`, `minDomains`, `matchLabelKeys`; cluster defaults spread by hostname (maxSkew 3) and zone (maxSkew 5) with ScheduleAnyway for pods that set none; constraints are not re-balanced on scale-down.
- [verified 2026-11-08 · src: https://kubernetes.io/docs/tasks/configure-pod-container/configure-service-account/] `automountServiceAccountToken: false` on the ServiceAccount or the Pod (the Pod wins); tokens come from the TokenRequest API with bounded lifetimes, rotated past 80 % of TTL or 24 hours, revoked 60 s after pod deletion.
- [verified 2026-11-08 · src: https://kubernetes.io/docs/concepts/containers/images/] Default `imagePullPolicy` is `Always` for `:latest` or no tag, `IfNotPresent` for any other tag or a digest; "You should avoid using the :latest tag when deploying containers in production"; digests are immutable.
- [verified 2026-11-08 · src: https://kubernetes.io/docs/concepts/configuration/overview/] Prefer Deployments to naked Pods, YAML over JSON, one file per set of related objects, omit defaults Kubernetes already applies, `kubectl apply -f dir/ --server-side`.

## NetworkPolicy
- [verified 2026-11-08 · src: https://kubernetes.io/docs/concepts/services-networking/network-policies/] A NetworkPolicy has no effect without a network plugin that enforces it; pods are non-isolated by default; `podSelector: {}` selects every pod in the namespace; `policyTypes` defaults to Ingress (plus Egress when egress rules exist); default deny all is `podSelector: {}` with `policyTypes: [Ingress, Egress]` and no rules.

## Ambient and sidecar
- [verified 2026-11-08 · src: https://istio.io/latest/docs/ambient/overview/] ztunnel is a per-node Rust proxy scoped to L4 (mTLS, authentication, L4 authorization and telemetry) over HBONE (HTTP CONNECT); waypoints are Envoy L7 proxies outside application pods, enabled per namespace, installed and scaled separately; traffic management, L7 authorization, L7 telemetry and VirtualService routing need a waypoint.
- [verified 2026-11-08 · src: https://istio.io/latest/docs/ambient/architecture/traffic-redirection/] ztunnel runs as a DaemonSet in `istio-system`; the istio-cni node agent redirects outbound TCP to port 15001, inbound plaintext to 15006 and inbound HBONE to 15008; ambient works beside any CNI.
- [verified 2026-11-08 · src: https://istio.io/latest/docs/ambient/usage/waypoint/] A waypoint is a Gateway with `gatewayClassName: istio-waypoint` and a listener `mesh` on port 15008 (HBONE); `istioctl waypoint apply -n NS --enroll-namespace` creates it and labels the namespace; enrolment is the `istio.io/use-waypoint=<name>` label on a namespace, Service or pod; `istio.io/waypoint-for` is `service` (default), `workload`, `all` or `none`; Gateway API CRDs must be installed first.
- [verified 2026-11-08 · src: https://istio.io/latest/docs/ambient/usage/add-workloads/] Workloads join ambient with the `istio.io/dataplane-mode=ambient` label on the namespace or the pod, without a restart; a pod with a sidecar is not placed in ambient; mixing modes within one namespace is not recommended.
- [verified 2026-11-08 · src: https://istio.io/latest/docs/overview/dataplane-modes/] Not yet in ambient: sidecar-to-waypoint interoperability, multi-cluster, multi-network, VMs; extensibility is WebAssembly on waypoints only and "EnvoyFilter API not supported"; no tracing at L4; both modes may coexist in one mesh per namespace.
- [verified 2026-11-08 · src: https://istio.io/latest/docs/setup/upgrade/canary/] Canary upgrades: `istioctl install --set revision=1-31-4` (no dots), namespaces move with `istio.io/rev=<revision>` after removing `istio-injection` (which takes precedence), workloads restart, `istioctl tag set default --revision 1-31-4` makes it the default, `istioctl uninstall --revision <old> -y` removes the old plane.
- [verified 2026-11-08 · src: https://istio.io/latest/docs/setup/additional-setup/sidecar-injection/] `istio-injection=enabled` injects at pod creation; existing pods must be recreated; the pod label `sidecar.istio.io/inject: "false"` opts out.

## mTLS and identity
- [verified 2026-11-08 · src: https://istio.io/latest/docs/reference/config/security/peer_authentication/] PeerAuthentication modes UNSET (inherit, else PERMISSIVE), DISABLE, PERMISSIVE (plaintext or mTLS), STRICT (mTLS only); the mesh-wide policy lives in the root namespace (`istio-system`) without a selector; selector policies in the root namespace are ignored; `portLevelMtls` keys are workload ports, not Service ports.
- [verified 2026-11-08 · src: https://istio.io/latest/docs/tasks/security/authentication/mtls-migration/] Istio defaults to PERMISSIVE; lock down a namespace with a PeerAuthentication named `default` with `mtls.mode: STRICT`, then the mesh with the same in `istio-system`; in PERMISSIVE plaintext traffic "bypasses authentication and authorization checks by default".
- [verified 2026-11-08 · src: https://istio.io/latest/docs/reference/config/security/authorization-policy/] Peer identities are `<TRUST_DOMAIN>/ns/<NAMESPACE>/sa/<SERVICE_ACCOUNT>` derived from the peer certificate, which requires mTLS; the SAN is `spiffe://cluster.local/ns/<ns>/sa/<sa>`.
- [verified 2026-11-08 · src: https://istio.io/latest/docs/reference/commands/pilot-agent/] Workload certificate lifetime is `SECRET_TTL`, default 24h, renewed at half the lifetime (`SECRET_GRACE_PERIOD_RATIO` 0.5).
- [verified 2026-11-08 · src: https://istio.io/latest/docs/reference/config/networking/destination-rule/] DestinationRule `tls.mode`: DISABLE (no TLS to the upstream), SIMPLE, MUTUAL, ISTIO_MUTUAL (Istio certificates, every other TLS field empty); `insecureSkipVerify` defaults to false.
- [verified 2026-11-08 · src: https://istio.io/latest/docs/ops/common-problems/security-issues/] An extra `-` before `from:` makes a separate rule (rules are OR); HTTP-only fields never match raw TCP ports; `istioctl x authz check` lists the policies applied to a pod; AUDIT never denies.

## AuthorizationPolicy
- [verified 2026-11-08 · src: https://istio.io/latest/docs/reference/config/security/authorization-policy/] Actions ALLOW (default), DENY, AUDIT, CUSTOM; evaluation: CUSTOM deny wins, then any DENY match denies, then no ALLOW policy means allow, then an ALLOW match allows, otherwise deny.
- [verified 2026-11-08 · src: https://istio.io/latest/docs/reference/config/security/authorization-policy/] `rules` unset: "the match will never occur" (an ALLOW policy with `spec: {}` allows nothing and denies all requests to the namespace); "An empty rule is always matched": `rules: - {}` allows all requests.
- [verified 2026-11-08 · src: https://istio.io/latest/docs/reference/config/security/authorization-policy/] `source.principals` and `source.namespaces` come from the peer certificate; `to.operation` has `hosts` (HTTP only), `ports`, `methods`, `paths` (`{*}`, `{**}`); `when` keys such as `request.auth.claims[iss]`; `targetRefs` (Gateway, GatewayClass, Service on waypoints, ServiceEntry) is exclusive with `selector`; a policy in the root namespace applies mesh-wide.
- [verified 2026-11-08 · src: https://istio.io/latest/docs/concepts/security/] A workload with no authorization policy allows all; the recommended start is an "allow-nothing" ALLOW policy with no rules, then incremental allows; identity fields need STRICT mTLS.
- [verified 2026-11-08 · src: https://istio.io/latest/docs/reference/config/security/request_authentication/] RequestAuthentication validates JWTs but "A request that does not contain any authentication credentials will be accepted"; requiring a token needs an AuthorizationPolicy with `source.requestPrincipals: ["*"]`.
