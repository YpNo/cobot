# Owner ideas, third review — 2026-11-07

Ten ideas the owner raised after the cartridge-os dogfood, each challenged, with the action the
partner proposes. **Confirmed as written by the owner on 2026-11-07**; rows 17–25 of
`docs/01-decisions.md` are firm. Applied the same day: rules 18 and 22 in `default.rules`, the
PR unit and architecture choice in `spec`, task commits in `build`, the pre-PR currency check and
the single PR in `wrap`, `Deps added:` in the builders' reports, the trigger matrix in
`expert-gha`. The rest is scheduled in design §15.

| I-1 | CI runs every test on every pipeline (PR, merge, release). Run tasks only where relevant. | Right goal, wrong lever if it means "fewer tests". The waste is in **triggers and stages**, not in the suite. Path filters alone are dangerous: a required check that is skipped reads as green, and a shared module changed under a filter escapes its dependents. | Encode a **trigger matrix** in `expert-gha` (and later a shared `expert-cicd` core): PR = lint, type check, tests of the changed areas via dependency-aware selection (`cargo test -p` plus dependents, `go list -deps`, nx/turbo affected), security scan; `concurrency` with cancel-in-progress. Merge to `main` = full suite once, build the artifact once, attest it. Release = **no test rerun**: verify the tag's commit passed `main` CI (`gh run list --commit`), reuse or rebuild the artifact reproducibly, sign, publish. Nightly or weekly = full matrix and dependency audit. Always one aggregator job (`ci-ok`, `if: always()`) that fails when a needed job failed and passes when one was legitimately skipped, so branch protection has a single required check. Avoid `tj-actions/changed-files` (compromised March 2025); use GitHub's own `paths` or `dorny/paths-filter` pinned by SHA. Our own `ci.yml` double-runs today (push to `main` and PR on the same commit); fix it when the remote exists. |
| I-2 | No `Co-Authored` line in commits, no "Claude" mention in PR bodies. | Already a standing rule (memory, commits since R0). A **word ban** would hurt this very repository, whose PRs legitimately describe a Claude Code plugin. The rule is about **authorship attribution**, not the word. | Keep the rule as "no attribution footer, no AI named as author". Enforce in depth: default layer `never Bash(git commit*Co-Authored-By*)` and `never Bash(gh pr create*Generated with*)` (argv-visible forms), the `contribute` skill's PR template, and a `wrap` check on the commit log before a PR. `--body-file` escapes the gate: the skill, not the gate, owns that path. |
| I-3 | Hexagonal architecture for backends, unless another is clearly better or the host project already has one. | Hexagonal pays off when there are real external adapters and a need for in-memory test doubles. It is overhead for CLIs, scripts, small libraries and bare-metal code (cartridge-os): indirection without a second adapter. Contributions must follow the host's architecture without exception, which the upstream rules already say. | Tie it to **profile**: `service` → hexagonal by default (domain, ports, adapters, in-memory test doubles); `cli`, `library`, `embedded` → plain layering with a port only at a true boundary. Decision criterion written down: two or more external adapters, or a test that needs a substitute, means ports. Lives in the `spec` principles check (options and recommendation, crissp idea) and an ADR template; language shapes (Rust modules per port, Go `internal/` packages, Python packages) in each `lang-*` skill. |
| I-4 | Fewer branches and PRs per session; consolidate tasks and topics; think global. | Collides with "one concern per PR" in the global instructions and with revert granularity, but both can hold at different levels. Big PRs cost review attention and conflict time; the mitigation is atomic commits inside them, not more PRs. Upstream contributions are the exception: maintainers want small PRs, follow their CONTRIBUTING. | Define the unit: **one spec = one branch = one PR**; **one task = one commit** (Conventional Commits, each revertable). Draft PR opened early for visibility. Security fixes and upstream PRs stay small. `spec` sizes the PR, `build` commits per task, `wrap` opens or updates the one PR. Also fewer PRs means fewer pipeline runs (I-1). This repository switches from direct commits on `main` to branch-per-spec once the remote exists. |
| I-5 | Check dependency and engine currency before a new session or topic, not on every exchange; the usual moment is just before a PR. | Checking upstream for every dependency is network-bound and noisy; doing it at session start every time contradicts "not every exchange". The right design is a **cached check with explicit triggers**. Reporting stays the deliverable: upgrades are the owner's call (global instructions). | Future `partner-deps check`: per-repository cache keyed by lockfile hash and date; runs at `onboard`, at session start only when the cache is older than seven days or the lockfile changed (one brief line: "3 of 41 dependencies behind, 1 advisory"), and always in `wrap` before the PR. Uses the ecosystems' own tools (`cargo outdated`/`cargo deny advisories`, `go list -m -u`, `npm outdated`, `uv pip list --outdated`, `terraform providers lock` dry run), no extra service. Dependabot or Renovate covers the continuous side in CI. |
| I-6 | Least dependencies; only when relevant. | Already a principle; what is missing is a **gate**. Adding a dependency is a decision, and builders currently can run `cargo add` or `npm install foo` unasked. | Default layer `ask` on dependency-adding commands: `cargo add`, `cargo install`, `npm install <pkg>` / `npm i <pkg>` (bare `npm install` stays silent), `pnpm add`, `yarn add`, `go get`, `uv add`, `pip install`, `poetry add`. `spec` lists every new dependency with its justification; builders report `Deps added:` and may not add one the spec does not name. |
| I-7 | Expert updater: when (re)starting on a project, check whether best practices and tools evolved, and whether a tool became deprecated or unmaintained. | This is the learner (decision 13) plus a **freshness trigger**. Unmaintained detection, by contrast, is cheap and deterministic (last release date, archived flag). | Knowledge skills carry dated lines already. Unmaintained check folded into `partner-deps` (I-5). The learner and this pipeline are the **prerequisite** for scaling the roster (I-8, I-9): without them fifteen experts rot. |

One `lang-typescript` skill carries the shared ground (TypeScript, Node and Bun, pnpm, vitest, eslint flat config or biome, tsconfig strictness); frameworks are thin, path-triggered skills on top (`*.vue`; `next.config.*` and `app/`; `*.tsx`). ## Addendum, 2026-11-07: containers, Kubernetes, service mesh

The owner added Docker, Podman, Kubernetes, and service meshes (Istio, Cloud Service Mesh on
GCP). Challenge: one "platform" expert would be too broad and would age at three different
speeds (Dockerfile practice is slow, Kubernetes ships three minors a year, Istio one every three
months). Three experts, each behind the learner's refresh cycle. Images belong to release
engineering, so `expert-containers` arrives with `ship`; Kubernetes arrives with the GCP expert
because the owner's clusters are GKE; the mesh comes after the cluster expert it depends on.
Cloud Service Mesh is Istio with a managed control plane, so it is a section of the mesh expert,
not a fourth one. Gate rules land now: mutating `kubectl` verbs, `helm install|upgrade|
uninstall|rollback|push|repo add`, `istioctl install|upgrade|uninstall|x`, `gcloud container
fleet mesh`, and image `push`, `prune`, `rm`, `rmi`, `login` ask; `docker build`, `helm
template|lint`, `kustomize build`, `istioctl analyze` and every read stay silent. Decision 26.
